<objective>
Ship the App Store review upsell: at every 3rd successful tool output (count 3, 6, 9, ...) the
**appstore** build asks the OS for a review via **StoreKit 2 `AppStore.requestReview(in:)`** at the
next natural pause — never more often than once per 7 days. The **direct** build gets nothing,
proven mechanically (chunk-module fold-in guard + sentinel, `strings` on the built binaries,
runtime no-invoke, prefs-observable e2e).

Purpose: turn real delivered value into App Store ratings without violating Apple 5.6.1 (OS
mechanism only, no incentive, no feature gating) and without polluting the direct channel.

Output: one shared counting seam (13/13 tools) keyed on OUTPUT CONTENT, an appstore-only prompt
core with a serialized boundary + 7-day-gap gate over an injectable clock, a new appstore-only Rust
command backed by a tiny Swift bridge, a direct-build absence guard + sentinel, unit + e2e
coverage, a `docs/CHANNELS.md` row, and the origin todo closed.

**Revision note (2026-08-08):** this plan was revised after `/codex:adversarial-review` over the
committed plan (98e7ca21). Three accepted findings changed the design — success identity is now a
content digest rather than a size/timing tuple (Task 2), the request is claimed by a
re-read claim at the final gate plus a process-level native guard (Tasks 1 and 3 — that claim's
stamp ordering AND its once-ever semantics are superseded by the revisions below), and the
deprecated `SKStoreReviewController` is replaced by StoreKit 2 via a Swift bridge (Task 3).

**Closing revision (2026-08-08, second Codex round).** Two further accepted findings changed the
design: (1) **stamp-after-success** — the request stamp (now `lastReviewRequestAt`) is persisted ONLY after
`platform.review.request()` RESOLVES. Concurrent callers are deduped by the in-memory
queue/pending claim, not by an early stamp; any native failure (run_on_main_thread failure, Swift
`Unavailable`, no window/anchor) persists nothing and RELEASES the native claim, so the next
3rd-success boundary retries instead of consuming the 7-day gap on a request the OS never
received. (2) **full-output digest at settle time** — the identity hashes the ENTIRE output
string, computed inside the 3 s quiet-window callback rather than on the render path. At
settle-time frequency a 2 MB scan (a few ms, once per window) is irrelevant, so the 4 KB
head/tail truncation and its blind spot (equal-length, middle-only differences — realistic for
large JSON/XML) are removed.

**Cadence revision (2026-08-09, user-locked — SUPERSEDES the one-shot design).** The prompt is no
longer once-ever. It fires at EVERY 3rd-success boundary (`toolSuccessCount` 3, 6, 9, ...) gated by
a MINIMUM 7-DAY GAP since the last SUCCESSFUL request. Threaded through every task below: (a) the
prefs field is `lastReviewRequestAt` (a recurring rate-limit stamp), not `reviewPromptRequestedAt`
(a one-shot claim); (b) the counter keeps incrementing forever — clamped only at a large ceiling
deliberately chosen NOT to be a multiple of 3 — and the boundary test is
`count % SUCCESS_INTERVAL === 0 && count > 0`; (c) the module-level `done` forever-latch is
DELETED, leaving the promise-chain queue as the only in-memory concurrency guard; (d) the 7-day
comparison reads an INJECTABLE clock (defaulting to `Date.now`), mirroring the license `_with_clock`
seam, so no test depends on wall-clock time; (e) the Rust `AtomicBool` is demoted from a once-ever
guard to an IN-FLIGHT guard — claimed on entry and ALWAYS released on completion, success or
failure — because "never twice" is now the webview's persisted gap gate, not the native layer's
job. "Only if the user never reviewed" is delegated to the OS: StoreKit exposes no
submitted-a-review signal, `requestReview` silently no-ops for users who already reviewed, and
macOS caps actual prompts at 3 per 365 days however often we ask. Everything else in this plan —
the StoreKit 2 Swift bridge, the full-output settle-time digest, the stamp-after-success ordering,
and every absence proof — is UNCHANGED.
</objective>
