<objective>
Add the shared large-paste guard (SC6 / carried PRT-04) to the async formatting hook so a multi-MB paste can never enter the Prettier/esbuild main-thread engine path and freeze the UI, contradicting the <2s paste-instant promise.

This is the ONLY shared-file change in Phase 33. It lives in `useAsyncFormat` (D-03) as an optional `maxInputBytes` param defaulting to a shared 2 MB constant. Oversized input short-circuits to an `ok:false` `FormatResult` BEFORE the debounce/runner — mirroring the existing empty-input short-circuit.

Crucially, oversize is detected with a BOUNDED UTF-8 byte counter (`utf8LenBounded`) that walks the input accumulating byte widths and returns `null` the INSTANT the running total exceeds the cap — so the guard NEVER runs a full `TextEncoder.encode` of a pathological paste just to measure it. The cap is in UTF-8 BYTES; the old `input.length` (UTF-16 code-unit) fast-path was WRONG for multibyte input (an all-3-byte string with `input.length <= cap` but `3 * input.length > cap` fell through to a full `byteLen(input)` encode before rejection — the 4th Codex finding). The bounded counter closes this for ASCII and multibyte alike: the only byte work on an over-cap input is bounded by the cap, and stops the moment the cap is crossed.

The counter MUST also be byte-for-byte identical to `TextEncoder.encode` for MALFORMED (lone/unpaired) surrogates — the 5th Codex finding. It consumes a second code unit ONLY when the next unit is a genuine LOW surrogate (0xDC00–0xDFFF); an unpaired HIGH surrogate, or a lone LOW surrogate, counts as 3 bytes (TextEncoder emits U+FFFD = 3 bytes) WITHOUT skipping the following unit. The naive "every high surrogate is a 4-byte pair, always `i++`" form UNDER-counts a crafted string like `"\uD800€"` (counts it as 4 bytes and swallows the `€`, when TextEncoder emits 6: U+FFFD 3 + `€` 3). Repeated enough, that under-count keeps `isOversize` false while the true UTF-8 length exceeds the cap → the over-cap payload reaches the synchronous runner = exactly the DoS SC6 exists to prevent, reachable via a malformed-surrogate paste. The pair-guard closes it: NO over-cap input of ANY kind can slip past.

The hook ALSO returns the input byte count it already knows (`inputBytes`) so that a consuming tool (Plan 03) reads size straight from the hook and NEVER recomputes `byteLen(input)` itself. This closes the real seam the second Codex round caught: if the tool kept the sibling `result.ok ? result.inputBytes : byteLen(input)` pattern, an over-cap `ok:false` paste would fall to `byteLen(input)` — a full multi-MB encode in the mounted render path — negating this hook-level fix. By centralising size in the hook (returning `undefined` for the over-cap case, where the byte count is deliberately left unmeasured), there is ZERO full-string encode of an over-cap input anywhere in the render path. Phase 34 (JS/TS) inherits both the guard AND this metadata verbatim. The sync JSON/XML tools are deliberately NOT retrofitted this phase (deferred idea, not scope creep).

Purpose: close the Codex adversarial-review carry-forward (unbounded main-thread work) at the shared seam both Prettier tools consume — without the guard itself, OR any downstream tool, doing heavy work (a full encode) on the pathological input it is meant to reject, for ANY input class (ASCII, multibyte, or malformed surrogates).
Output: a guarded `useAsyncFormat` that also exposes `inputBytes`, plus its SC6 acceptance test proving 0 runner calls for over-cap, the bounded-counter no-full-encode invariant for multibyte over-cap input, the malformed-surrogate no-bypass invariant, exact TextEncoder parity for unpaired surrogates, and the inputBytes-mapping contract.

       // allocating/encoding the whole string. Work is O(min(n, max)), bounded by the

       function utf8LenBounded(s: string, max: number): number | null {
         let bytes = 0;
         for (let i = 0; i < s.length; i++) {
           const c = s.charCodeAt(i);
           if (c < 0x80) bytes += 1;
           else if (c < 0x800) bytes += 2;
           else if (
             c >= 0xd800 && c <= 0xdbff &&              // high surrogate …
             i + 1 < s.length &&
             s.charCodeAt(i + 1) >= 0xdc00 &&           // … immediately followed by a

         }
         return bytes;
