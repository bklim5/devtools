<objective>
Golden-lock all FOUR JS/TS dialects (js, ts, jsx, tsx) so the combined-tool promise
is RED-on-drift (D-09), AND byte-DRIFT-lock the ACTUAL output of the no-picker path the
mounted tool uses — `formatJsTs` (typescript-first, babel-on-error from 34-01) — not just
the named parsers. (The routing ORDER contract — typescript-before-babel — is proven by
34-01's injectable-runner order test; byte goldens can't see a babel-first mis-route.)
The existing suite already locks messy.js (babel) and messy.ts (typescript);
this adds messy.jsx (babel) + messy.tsx (typescript) fixtures + goldens, a `.jsts.golden`
drift-golden set that byte-locks `formatJsTs`'s output for every dialect, and a
`fallback.js` fixture (valid JS the TS parser rejects) whose babel-parser golden proves
the fallback chain fires and its output is pinned.

Purpose: Named-parser goldens can stay green while the tool ships non-canonical output —
`formatScript(x, "babel")` is locked, but the tool never calls it: it calls `formatJsTs`,
which tries `typescript` first and only falls back to `babel` on a parse error. This plan
DRIFT-locks formatJsTs's real output (catches version/option drift) and proves the babel
fallback FIRES (fallback.js). It does NOT prove the ts-before-babel ORDER — byte goldens
CANNOT, since typescript and babel emit byte-identical output for common JS (verified at
pin 3.8.3); that order contract is proven by the injectable-runner ORDER test in 34-01.
The user explicitly wants JSX/TSX first-class (D-09), and the no-picker fallback IS the
coverage mechanism (D-01/D-04).

Output: two new dialect fixtures + goldens, four routing goldens, one fallback fixture +
golden, the generator entries, and the parity cases (named + routing + fallback). This
plan imports `formatJsTs` from 34-01 → Wave 2, depends_on ["01"]. It shares no files with
34-04 (fixtures/generator/parity test vs tool/registry), so the two run parallel in Wave 2.
</objective>
