<objective>
Make launch-at-login FULLY ABSENT from the store build's General pane (D-04), no-op the autostart platform seam under `IS_APPSTORE` as belt-and-suspenders (D-05), ADD the load-bearing D-03 proof (an explicit assertion that the store boot path invokes no `platform.license.*` IPC — so Plan 29-01's Rust compile-out is provably safe; string grep is INSUFFICIENT per the `keygen-compileout-d04-proof` learning), AND — the Phase-29 revision (iteration 2) — REMOVE THE ENTIRE App-shell updater surface from the store build by EXTRACTING it into a new direct-only component and gating it behind a build-time IS_APPSTORE lazy-import switch.

**Why iteration 2 supersedes the prior per-effect gating:** the Phase-28 work gated the Updates *pane* (StoreUpdatesSettings) but left the App.tsx SHELL-LEVEL updater overlay UNCONDITIONAL. A fresh store install has `autoUpdateCheck === null`, so `needsOptInPrompt(null) === true` → the store build would RENDER the "Enable automatic update checks?" opt-in prompt on first launch — forbidden self-update UI (App Store guideline) and, once the effects were per-effect-gated, DEAD (clicking "Yes" sets a pref nothing reads). A prior plan revision proposed gating just the launch-check + menu-listener EFFECTS under `!IS_APPSTORE`; that is INCOHERENT — it leaves the opt-in prompt, the UpdateBanner, the `useUpdater` state machine, and `shell/update` JS all shipping in the store bundle (not tree-shaken). This plan REPLACES that approach: move the WHOLE updater surface into `src/components/UpdaterOverlay.tsx` and mount it ONLY in the direct build via the same `lazy(() => import(...))` tree-shake idiom App.tsx already uses for `UpsellSurface` — so the store bundle contains NONE of the updater UI by construction (no dead UI, no opt-in prompt).

**What the extraction does and does NOT remove (iteration 3 clarity).** The extraction tree-shakes the updater UI subtree (UpdaterOverlay → useUpdater → shell/update → UpdateBanner) out of the store bundle. It does NOT remove the `@tauri-apps/plugin-updater` plugin JS itself: `tauri.ts` imports it at TOP LEVEL (line 21) and `index.ts` loads `tauri.ts` via one shared dynamic `import("./tauri")` that BOTH builds load via `initPlatform()`, so the inert plugin JS rides along in the shared seam — exactly like `plugin-autostart` (tauri.ts line 26), which D-05 ALREADY ACCEPTS (D-05 = runtime no-op, not bundle removal). The load-bearing safety proof is therefore the RUNTIME no-invoke assertion (`platform.updater.check` called 0 times on the store boot path), NOT bundle exclusion of the plugin package — mirroring `keygen-compileout-d04-proof`.

The store build has no autostart plugin REGISTERED (compiled out Phase 27), no license commands (Plan 29-01 Task 2), and no updater command REGISTERED (compiled out Phase 27; the surviving tray item gated out in Plan 29-01 Task 3). With the overlay extracted + gated out, the store frontend never imports `useUpdater`/`shell/update`/`UpdateBanner` and never calls `platform.updater.check()` / `platform.events.onMenuCheckUpdates`. With launch-at-login absent there is no call path to the autostart plugin — D-05 hardens it. The D-03 assertion proves the shared `tauri.ts` license/updater IPC literals (which ride along in the bundle because the `iap` arm imports the whole `tauriPlatform` object) are NEVER invoked in the store boot path.

Purpose: MAS-NATIVE-04 (launch-at-login hidden/absent) + the runtime-safety + dead-UI half of MAS-NATIVE-03 (no unregistered-command invoke at boot, no forbidden self-update UI) + MAS-NATIVE-02 (the kept tray's frontend wiring must not drive a compiled-out command).
Output: an `IS_APPSTORE`-gated General pane; an `IS_APPSTORE` no-op autostart seam; a NEW `UpdaterOverlay.tsx` owning the whole updater surface, mounted only in the direct build via an `IS_APPSTORE`-gated lazy import; a boot-path no-license-IPC + no-updater-IPC test; App-level tests proving the store build renders no opt-in/banner and registers 0 updater listeners; a direct-build real-WKWebView e2e (update.e2e.ts) proving the extracted overlay's banner still renders deterministically.
