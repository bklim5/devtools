<objective>
Build the HTML formatter tool (PRT-07/08) — a thin `src/tools/html-formatter/` cloned from `xml-formatter/` but the FIRST async-hook consumer: it drives the shared `useAsyncFormat` (with the Plan-01 size guard) using a runner that dispatches `mode === "minify" ? minifyHtml(input) : formatHtml(input, { indent, printWidth })`, supplies `onPrintWidth` so the Width segment shows, and wires the async `pending` "Formatting…" hint through the StatusBar. Register it registry-only (PRT-12) so sidebar / ⌘K / HashRouter auto-derive; ships free (no entitlement gate).

Critically, this tool reads its `byteCount` straight from the hook's returned `inputBytes` (Plan-01) instead of cloning the sibling `result.ok ? result.inputBytes : byteLen(input)` pattern. That sibling pattern is a trap on the async guarded seam: on an over-cap paste the result is `ok:false`, so `byteLen(input)` would run a full multi-MB `TextEncoder.encode` in the MOUNTED render path — exactly the allocation the Plan-01 hook guard is meant to avoid. By consuming `inputBytes` (which is `undefined` for over-cap), the mounted tool does ZERO full-string encodes of an over-cap input, and the Plan-01 guard actually holds at the real user-facing seam — for ASCII, multibyte, AND malformed-surrogate over-cap inputs alike (Plan-01's bounded counter rejects all three without a full encode; this tool must not re-introduce one).

Because `inputBytes` is `number | undefined`, this plan ALSO widens the shared shell's `FormatterView.FormatterStatus.byteCount` from REQUIRED `number` to OPTIONAL `byteCount?: number` — a one-line, semantically-safe widening (StatusBar already renders no size readout when byteCount is not a number, and its own prop `StatusBarProps.byteCount` is already optional; every existing json/xml caller passes a concrete number). Without it the tool's `const byteCount = inputBytes;` fails this plan's own `npx tsc --noEmit` gate, and the only tsc-green alternative — coercing `undefined → 0` — would REGRESS the over-cap behavior (StatusBar would print "0 bytes" instead of suppressing the readout). The CONTEXT assumption "FormatterView needs no change" is wrong for exactly this over-cap case; this is the ONLY FormatterView change (in-scope shell work — the engine files prettier/minify/types.ts stay untouched).

Purpose: the mounted tool that finally exercises the P32 async seam (pending hint + first lazy-chunk load) on a real paste, surfaces the Plan-01 guard as a calm role=alert "too large" status WITHOUT re-encoding the over-cap input, AND renders engine errors as line:col (D-11 — the malformed-HTML case carries a real column, so the tool MUST mirror the JSON tool's line:col mapping, not the XML tool's line-only form).
Output: HtmlFormatterTool + registry entry + a one-line FormatterView status-type widening + unit tests (incl. a tool-level SC6 0-encode proof over ASCII, multibyte, AND malformed-surrogate over-cap input).
</objective>
