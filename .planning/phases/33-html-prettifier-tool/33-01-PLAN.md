<objective>
Add the shared large-paste guard (SC6 / carried PRT-04) to the async formatting hook so a multi-MB paste can never enter the Prettier/esbuild main-thread engine path and freeze the UI, contradicting the <2s paste-instant promise.

This is the ONLY shared-file change in Phase 33. It lives in `useAsyncFormat` (D-03) as an optional `maxInputBytes` param defaulting to a shared 2 MB constant. Oversized input short-circuits to an `ok:false` `FormatResult` BEFORE the debounce/runner — mirroring the existing empty-input short-circuit. Crucially, oversize is detected FIRST via a cheap `input.length` pre-check (UTF-16 code-unit count is always <= UTF-8 byte length), so a pathological multi-MB paste is rejected WITHOUT a full `TextEncoder.encode` allocation just to measure it. Phase 34 (JS/TS) inherits the guard verbatim (roadmap intent). The sync JSON/XML tools are deliberately NOT retrofitted this phase (deferred idea, not scope creep).

Purpose: close the Codex adversarial-review carry-forward (unbounded main-thread work) at the shared seam both Prettier tools consume — without the guard itself doing heavy work on the pathological input it is meant to reject.
Output: a guarded `useAsyncFormat` + its SC6 acceptance test proving 0 runner calls for over-cap input and the cheap-vs-exact measurement split.
</objective>

    - Over-cap input (isOversize): the effect never schedules a run (runner call count stays 0); the returned `result` is `{ ok:false, error:{ message } }`; `pending` is false. The message has TWO forms depending on which branch rejected it:
        · Cheap pre-check path (rejected on `input.length > maxInputBytes`, exact bytes NOT computed) → `Input too large (> 2 MB) — 2 MB max`.
        · Exact path (rejected on `byteLen`, exact bytes known) → `Input too large (X.X MB) — 2 MB max` where X.X = (exactBytes/1_000_000).toFixed(1).
    - The exact `byteLen` (full `TextEncoder.encode` allocation) is NEVER called when `input.length` already exceeds `maxInputBytes` — the cheap pre-check short-circuits, so a pathological multi-MB paste is not encoded merely to be measured (this is the actual DoS fix, not just the runner skip).
    - Empty/whitespace still returns EMPTY_OK (empty check wins over oversize — an empty string is never "too large").
    - A custom `maxInputBytes` (e.g. small value in a test) is honored on BOTH branches.
  </behavior>

    Extend `useAsyncFormat` with a 4th optional parameter `maxInputBytes: number = MAX_FORMAT_INPUT_BYTES`.

    1. Export a new constant at module top (next to `DEBOUNCE_MS`):
       `export const MAX_FORMAT_INPUT_BYTES = 2_000_000;` with a comment: 2 MB UTF-8 (D-02) — comfortably covers real pasted HTML (~200–500 KB) while keeping the worst-case 4-plugin Prettier-with-embedded-code parse well under the <2s promise; messaged to the user as "2 MB".
    2. Import `byteLen` from `@/lib/format/types` (alongside the existing `FormatResult` type import).
    3. Compute, at render (after `isEmpty`), with a CHEAP allocation-light pre-check BEFORE any encode. UTF-8 byte length is ALWAYS >= the UTF-16 code-unit count (`input.length`), so `input.length > maxInputBytes` proves oversize WITHOUT encoding. Only when `input.length <= maxInputBytes` do you call the exact `byteLen(input)`:
       ```ts
       let isOversize = false;
       let exactBytes: number | undefined; // set ONLY when we actually encode
       if (!isEmpty) {
         if (input.length > maxInputBytes) {
           isOversize = true;               // cheap short-circuit — NO TextEncoder.encode
         } else {
           exactBytes = byteLen(input);     // exact count only when plausibly under cap
           isOversize = exactBytes > maxInputBytes;
         }
       }
       ```
       This is the load-bearing DoS fix: a multi-MB pathological paste is rejected on the O(1) `.length` compare and is NEVER fully encoded just to be measured.
    4. Derive the oversize `ok:false` result, memoized with `useMemo` keyed on `[isOversize, exactBytes, input.length]` so an identical over-cap render does not churn a new object. The message has TWO forms:

       - Exact path (`exactBytes !== undefined`): `` `Input too large (${(exactBytes / 1_000_000).toFixed(1)} MB) — 2 MB max` ``.
       Both keep the D-01/D-02 wording ("2 MB max", hard reject; the role=alert surfacing is the tool's job in Plan 03).
    5. Reset stale pending during render for oversize too: change the existing `if (isEmpty && pending) setPending(false);` to `if ((isEmpty || isOversize) && pending) setPending(false);`.
    6. In the effect, skip running when oversize: `if (isEmpty || isOversize) return;` (currently `if (isEmpty) return;`). Add `isOversize` and `maxInputBytes` to the effect dependency array `[isEmpty, isOversize, maxInputBytes, input, opts]`.
    7. Return: `result: isEmpty ? EMPTY_OK : isOversize ? oversizeResult : resolved` (keep `pending` as-is). Do NOT bump reqId differently — the existing cleanup already drops in-flight work when `input` changes into the oversize range.
    Keep the empty-input path and the latest-wins reqId gate byte-for-byte intact — this is purely additive.
