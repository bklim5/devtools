<objective>
Add the shared large-paste guard (SC6 / carried PRT-04) to the async formatting hook so a multi-MB paste can never enter the Prettier/esbuild main-thread engine path and freeze the UI, contradicting the <2s paste-instant promise.

This is the ONLY shared-file change in Phase 33. It lives in `useAsyncFormat` (D-03) as an optional `maxInputBytes` param defaulting to a shared 2 MB constant. Oversized input short-circuits to an `ok:false` `FormatResult` BEFORE the debounce/runner — mirroring the existing empty-input short-circuit. Crucially, oversize is detected FIRST via a cheap `input.length` pre-check (UTF-16 code-unit count is always <= UTF-8 byte length), so a pathological multi-MB paste is rejected WITHOUT a full `TextEncoder.encode` allocation just to measure it.

The hook ALSO returns the input byte count it already knows (`inputBytes`) so that a consuming tool (Plan 03) reads size straight from the hook and NEVER recomputes `byteLen(input)` itself. This closes the real seam the second Codex round caught: if the tool kept the sibling `result.ok ? result.inputBytes : byteLen(input)` pattern, an over-cap `ok:false` paste would fall to `byteLen(input)` — a full multi-MB encode in the mounted render path — negating this hook-level fix. By centralising size in the hook (returning `undefined` for the over-cap case, where the byte count is deliberately left unmeasured-cheaply), there is ZERO full-string encode of an over-cap input anywhere in the render path. Phase 34 (JS/TS) inherits both the guard AND this metadata verbatim. The sync JSON/XML tools are deliberately NOT retrofitted this phase (deferred idea, not scope creep).

Purpose: close the Codex adversarial-review carry-forward (unbounded main-thread work) at the shared seam both Prettier tools consume — without the guard itself, OR any downstream tool, doing heavy work on the pathological input it is meant to reject.
Output: a guarded `useAsyncFormat` that also exposes `inputBytes`, plus its SC6 acceptance test proving 0 runner calls for over-cap input, the cheap-vs-exact measurement split, and the inputBytes-mapping contract.
</objective>

```typescript
export const DEBOUNCE_MS = 180;
export const MAX_FORMAT_INPUT_BYTES = 2_000_000; // 2 MB UTF-8 (D-02)
export function useAsyncFormat<O>(
  input: string,
  opts: O,
  runner: (input: string, opts: O) => Promise<FormatResult>,
  maxInputBytes?: number, // defaults to MAX_FORMAT_INPUT_BYTES
): { result: FormatResult; pending: boolean; inputBytes: number | undefined };
// inputBytes: 0 when empty · undefined when over-cap (deliberately unmeasured-cheaply)
//             · resolved.inputBytes when ok · exactBytes when under-cap error.
// A consuming tool sets byteCount = inputBytes directly — it MUST NOT call byteLen(input).
```

```typescript
export function byteLen(s: string): number; // UTF-8 byte length = TextEncoder.encode(s).length (FULL allocation)
export type FormatResult =
  | { ok: true; output: string; inputBytes: number; outputBytes: number }
  | { ok: false; error: { message: string; line?: number; col?: number } };
```
